# M4: the demo and the measurements

**Status:** run 2026-11-05 on `silica-999936-macos-applesilicon` (macOS, Apple Silicon only), `127.0.0.1`, Erlang/OTP 28 only as the oracle of earlier milestones. A plain Silica service (node a) and a plain Silica client (node b), two separate operating-system processes, exchange casts over the M3 distribution layer. The payload uses every type the typed ETF codec supports; the service answers through a `reply_to` name; a node is stopped mid-run; hostile frames are injected; rate and peak memory are measured. **The receive step is still a stub** (section 7). Plan: [`mvp.md`](../mvp.md) section 5, milestone M4. Findings for the compiler: [`silica-defects.md`](../silica-defects.md) (SD-35, SD-36 and notes).

### The messages

Manifest of node a (node b is the mirror; the types are generated, shortened here):

```
node   a@127.0.0.1
peer   b@127.0.0.1 127.0.0.1 47421 listen
remote answers @ b@127.0.0.1 cast { n: int64, seq: int64, body: BODY }
local  svc cast { reply_to: atom, seq: int64, body: BODY }
```

`BODY` is seven records of two to four fields (grouped because of SD-36): `ints { i8, i16, i32, i64 }`, `uints { u8, u16, u32, u64 }` (the maximum `uint64`), `floats { f32, f64 }` (the `float32` is the exact widening of 0.1f), `scalars { flag: boolean, ch: char, who: atom, text: string }`, `comp { pair: (int8, string, boolean), one: { k: atom, v: int16, ok: boolean } }` (a tuple and a nested record), `lists { nums: List[int32], items: List[{ k: atom, v: int16, ok: boolean }], tags: List[string] }`, `more { fs: List[float64], blob: List[uint8], grid: List[List[uint8]] }` (a byte list is a STRING_EXT on the wire, as erl writes it). Every value is at an edge (minimum `int8`, `int16`, `int32`, an `int64` beyond 2^53, maximum `uint8`, `uint16`, `uint32`, `uint64`). A request is 547 bytes of ETF (computed with `term_to_binary` of the same term); a frame is about 600 bytes, 75 carrier parts.

### How a request travels

The client's `answers` actor (registered under `answers`, the name the request carries in `reply_to`) casts the request to the registered name `svc`; node b's proxy for `svc` encodes it and the writer sends it. On node a a deliverer decodes it and `cast_registered`s it to the plain actor `svc`, which compares the payload and casts its answer to the name in `msg.reply_to`: **on node a that name is the generated proxy for `answers`**, which encodes the answer and sends it back; on node b a deliverer delivers it to `answers`. Nothing in `svc` or `answers` knows about nodes: `cast_registered(msg.reply_to, resp impl ActorMessage {})`.

### The golden comparison

Each side re-encodes the value it received with the generated encoder and compares the bytes with the encoding of the value built from constants (`make_body`), so every field, floats and list elements included, is compared as the codec writes it. In addition, per-group `==` checks (`ints`, `floats`, `scalars`, `lists`) are printed. A **negative control** runs once on the client: the same comparison with the expected `n` changed by one must say "not equal" (it prints `a changed value is detected: true`), so the comparison is not vacuously true. The output of each program is then compared with its golden by the trial harness.

## 2. Results

`make -C trials/m4_demo integrate`: **7 passed, 0 failed**, three runs in a row (goldens for both sides of `demo`, `hostile`, `hostile_close`, and the client of `kill`). Each scenario is two separate processes, `a` started first.

| Scenario | What happens | Evidence in the goldens |
| --- | --- | --- |
| `demo` | b casts three requests one after another (reply_to `answers`); a answers each | a prints `service: request seq=N reply_to=answers intact=true payload ints=true floats=true scalars=true lists=true` for 1 to 3; b prints `client: answer n=N seq=N intact=true ...` for 1 to 3, `negative control, a changed value is detected: true`, `all answered, 3 requests, payload not intact in 0` |
| `kill` | the same, then the driver sends SIGKILL to node a once b has printed `answered,`; b's `ticker` (a plain actor that casts a request to `svc` every 300 ms from 3 s on) keeps sending | b: `[bees audit] link down, proxies ended; reason closed 3`, `proxy ended (killed)`, then **`ticker failed: actor_not_found`**: see below |
| `hostile` | b injects five hostile frames into the live link, one every 200 ms (after the three answers), then a good request (seq 900) | a audits each refusal (below) and then answers seq 900: the link is kept |
| `hostile_close` | the same five, then a frame whose length prefix is 65,536 | a audits `bad frame length, link closed length 65536`, closes; both sides see the link go down and their proxies end |

### A node stopped mid-run: only Silica's own rule

Node a is killed (SIGKILL, so no orderly close). Node b sees the connection end (`link down ... reason closed`), the reaper ends its proxy for `svc` (`proxy ended (killed)`, the M3 mechanism), and its `ticker`'s next `cast_registered(:svc, ...)` fails **the ticker** with the failure report `(:explicit, :actor_not_found)`: the one SD-33 already records for a cast to a name nobody holds. The report text is the reason Silica gives for any dead actor; the program's own reporter turns it into the line `ticker failed: actor_not_found` (it checks for the substring `actor_not_found` in the failure report, and prints `ticker failed: OTHER` for any other reason; the golden has the first). No new failure kind appears: nothing in the layer fails the sender in any way a dead local actor would not. What the sender must know: **the name is gone for good**: there is no reconnect (M3), so every later cast fails the sender again, and a supervisor that restarts the sender gets the same failure until the program restarts.

Not exercised: node **b** stopped while node a is answering. The same rule says the service actor `svc` would fail when it casts its answer to the dead `answers` proxy. That is a plain consequence of the rule, but it means a service that answers a remote client dies when the client's node is gone, which a service author may not want; whether BEES should offer a non-failing send to a remote name is a decision (section 6).

### Hostile frames: refused and audited, the link stays unless the framing is broken

`hostile` injects, through the node's writer (`bees_net@launch` returns it; `bees_net@send_raw` writes a built frame as it is), after the handshake, over the live link. Node a prints, in order:

| # | Frame | Audit line at node a | Link |
| --- | --- | --- | --- |
| 1 | payload first byte 130 instead of 131 | `payload refused bad_version 1` | kept |
| 2 | payload whose first map key is not a field of the type (one byte changed) | `payload refused unknown_field 14` | kept |
| 3 | payload cut short (5 bytes fewer than it says) | `payload refused truncated 2` | kept |
| 4 | a pid from another node (`x@127.0.0.1`) in the control message | `frame dropped foreign_actor 15` | kept |
| 5 | a target name nobody serves | `frame dropped unknown_atom 10` | kept |
| after | a good request (seq 900) | answered normally (`intact=true`) | kept |
| (`hostile_close`) | length prefix 65,536 | `bad frame length, link closed length 65536`, then `link down, proxies ended; reason closed`, `frames dropped - 6` | **closed** |

So the rule, as M3 decided it (decision 4): a violation of the **framing** (length, a frame before the handshake, a bad handshake message, an unlisted node) closes the link; a bad **content** of an intact frame is dropped, audited and counted, and the link continues. Nothing is delivered to the target for any of the six, and the audit never contains payload content. The refusal is silent toward the peer (no message back). These are five crafted classes and one framing violation, not a fuzzing campaign.

## 3. Measurements

**Method.** `make -C trials/m4_demo measure` starts node a (`dangerous_a_rate`) and node b (`dangerous_b_rate`) as two processes through `tools/run_demo.py --time --stamps`, each under `/usr/bin/time -l` (peak resident set size and peak memory footprint from the kernel's accounting of the child, written at its exit). The client sends **4,000 requests** (the full 547-byte payload), **8 in flight**: it casts eight at the start, and the answer to request s triggers request s+8. Every answer is compared with the golden (payload intact in all 4,000). Time is taken by the driver from the output lines `client: sending` and `client: all answered` (read from a pty, good to about 0.1 s). Timing roles are OTP's defaults (tick after 15 s idle, silence limit 60 s). **One run each, on one machine, with Silica's own trial suites sometimes running at the same time: this is not a benchmark.**

| | Run 1 (earlier build, same layer) | Run 2 (final build, the one in `make measure`) |
| --- | --- | --- |
| request/answer round trips | 4,000 in 357.7 s = **11.2 per second** (22.4 messages per second over the link) | 4,000 in 209.0 s = **19.1 per second** (38.3 messages per second) |
| node a peak resident set | 92.2 MiB | **90.1 MiB** (peak footprint 89.5 MiB) |
| node b peak resident set | 95.5 MiB | **95.0 MiB** (peak footprint 94.4 MiB) |
| node a CPU | user 308.9 s, sys 111.3 s | user 178.4 s, sys 74.8 s |
| node b CPU | user 301.4 s, sys 110.7 s | user 173.6 s, sys 72.6 s |
| time per 1,000 answers (run 2) | | 42.9 s, 54.0 s, 58.7 s, 53.4 s |

Reading the numbers honestly: the layer is **slow**, about 50 ms per round trip with a 600-byte frame each way, both nodes at 100 to 120 % CPU the whole time and the system share about 30 %. The cost is in the part-at-a-time design (75 parts per frame, a carrier request, a result event and an actor dispatch per part, M3 decision 2), in the per-dispatch growth of the assembler's memory (SD-35: every dispatch of an actor that keeps the list takes the whole-state copy, which is what the 18 million page reclaims of run 1 are), and in the O(n) list reads of the stub. Peak memory is flat, about 90 MiB per node, and does not grow with the number of requests (sampled at 25 s intervals, 11 to 69 MiB on the way). Small messages are much cheaper: the M3 handshake-and-one-cast trial (30-byte frames, a few dozen dispatches) measured 21 MiB and 0.00 s user, but no small-message rate was measured here; nothing should be read into it. `buf(uint8)` across the foreign-function boundary (one call per frame instead of per eight bytes) is where an order of magnitude would come from.

## 4. The state of memory before the fix, for the record

The first complete run of this milestone worked and was unusable: 480 MB resident at the third message, each message slower than the last (round trips 0.15 s, 0.38 s, 0.63 s), a 4,000-request run would not finish. The probe (SD-35): `get_actor_memory_usage` of each actor printed after nine seconds, `conn committed=726646784`, `tx 49152`, `answers 114688`; with a debug print at the start and end of every dispatch the committed memory was equal at the start and the end of a dispatch (it was not the dispatch's own stack) and grew by 1,048,576 bytes between dispatches, for `tx_credit` events (the node's own writes) as much as for `rx` (the parts of a received frame). `state_policy(:shrink_after_compaction)` on the connection actor changed nothing (745 MB). A small experiment ruled out the codec: `make_req`, `enc`, `validate_named`, `dec` and `req_intact` each run twenty times in one actor stay at 2 MB.

## 5. M3 layer changes (smallest fixes, and what each cost)

1. **The connection actor no longer holds a list** (the fix for the memory above). `conn` kept the parts of the frame body as a `List` in its state. Now the state is scalars and actor references only. When a length is read, `conn` spawns an assembler actor `asm` for that frame (`asm_for`), forwards each part of the body to it (`rx_body`), and waits (mode 5). `asm` keeps the list, and when the last part is in it builds the frame (`complete`: the stub `bees_ingress@recreate` and the same handling as before), reports the connection's new state in one `frame_result` event (the changes packed in the event's `n`: mode, step, peer, and how many frames were delivered or dropped) and ends. The wire behaviour is unchanged: M3's goldens are identical (section 8). The frame handling code is unchanged except for the type of `st` (`asm: actor_ref` where `ws: List` was).
2. **`bees_net@launch(c, tick_ms)`** returns `{ conn, tx }` (`start` is `launch` returning `conn`): the hostile-frame program needs the writer to inject a raw frame into a live link after the handshake. M3 had `raw_writer` for a program that never completes the handshake.
3. One new atom, `frame_result`, in `src/shim/bees_tcp.atoms`.
4. Not needed in the end, and left alone: the 4096-byte frame limit (the payload is 547 bytes), the one-link-per-node limit, the missing reconnect, the `FromPid` index (it is the proxy's index, 0 for the one proxy of each node).

## 6. Decisions to review

1. **The assembler actor and the forwarding of event data across actors.** It is part of the stub (section 7): the connection actor forwards each received part with an ordinary cast to `asm` and `asm` forwards the result as an event. M0's rule was that a handler does not forward foreign data; the stub already breaks it in spirit (M3 decision 1), and a compiler that checks handlers will reject both hops and the copy. When `recreate`/`decode` can be called, the receive step becomes one derived call and this actor structure may not be needed, if the derived call is cheap enough to run per frame in one dispatch.
2. **Result packing in `n`.** The `frame_result` event carries the new mode, step, peer and the two counter changes as `mode + 16 step + 256 (peer+1) + 65536 dok + 262144 ddrop`. It keeps the carrier's event type (the owner receives `{tag, n, reason, info}` and that type is the carrier's). A richer message would need a second actor in front of `conn`.
3. **A service dies when it answers a client that is gone** (not exercised, section 2). The alternative is a send that does not fail (a Silica feature request, like SD-33's `whereis`), or having each service answer through a short-lived deliverer the way BEES delivers (so the failure is the deliverer's). Open.
4. **The payload is seven groups, not one flat record**, because of the compile cost (SD-36). A real program with a 20-field message type should expect to hit the same wall until the compiler changes.
5. **The numbers printed are looked up, not converted** (`num_text`: 0 to 6, 900, 1000 to 4000 and `?`), because Silica has no integer-to-text conversion; the output lines are each one `println` so that another actor's output cannot split them. The audit lines of `bees_ingress@audit` are still several prints (a rare split is possible; none was seen in the stable runs).
6. **SIGKILL is the stop.** A graceful stop (the program ends, the OS closes the transport) is the same to the peer, since the closing is the kernel's; the orderly shutdown of the program's own actors is not tested.
7. **Timing roles in the scenarios**: 1 s tick, 3 s silence limit (`timing_kill.role`); the rate run uses OTP's 15 s and 60 s.
8. **Process-level test controls**: the `ticker` starts at 3 s and the kill happens about 0.5 s after the third answer, so the first cast of the ticker is always after the link is down (the goldens do not depend on a race), at the cost of not showing a cast that races the close.

## 7. Compiler findings

SD-35 (state with a heap value: about 1 MiB of committed memory per dispatch, never returned; a profile dominated by the stack zeroing at message return), SD-36 (the generated unit of one 22-field record did not compile in 300 s; the compiler ran out of memory in `type_surface_cache` for five entries each spelling the whole payload type forty times), `rec` a reserved word, E2003 for a `char` compared with a literal after `== true and`; the known E3010 rule again (an effect in `proc[...]` must be used by a builtin written in that sequence) and, while Silica's own suites ran on the machine, one compiler out-of-memory and one crash in a node leaf (each gone on the retry; the node Makefile builds twice). Details in [`silica-defects.md`](../silica-defects.md). `W2300` is now reported for the assembler `asm` only (`slot 'ws' is replaced without an update`), which is the point of the fix: a short-lived actor.

## 9. Not covered

- **The receive step is a stub and the language gives no taint guarantee.** `bees_ingress@recreate` copies the parts; it does not clear taint, and what protects the program is BEES's own validation (M3 section 3). The assembler adds another forwarding hop. The "hostile frame refused" result is about BEES's checks, not about Silica's taint rules; a compiler that checks handlers will reject this code until `recreate`/`decode` (SD-32) is callable. **Do not read this milestone as a security result.** No authentication, no encryption (banner printed), `127.0.0.1` only, macOS arm64 only, fixed port 47421.
- **Hostile input:** five crafted content cases and one framing case; no fuzzing; no slow-sender test (a peer that stalls with a frame half sent holds the link until the silence limit, M3 section 3); no oversized payload within the limit (4,000 bytes).
- **Rate and memory:** two runs of one scenario (full payload, window 8) on one machine under variable load; no small-message rate; no multi-node, no window sweep, no comparison with an Erlang node; no profile of where each 50 ms goes beyond the SD-35 finding.
- **A node stopped mid-run:** the service's node only (SIGKILL); node b stopped while a answers is argued from the rule and not run; no restart of the stopped node, no reconnect (the link and the proxies do not come back).
- **Stock Erlang node:** none connected (D34: a stock node authenticates with the cookie digest that BEES does not use; **planned: N2, D36**).
- **One live link per node**, one frame in flight per direction, frames up to 4096 bytes, control messages other than REG_SEND dropped and audited, `FromPid` a proxy index.
- **Any-type terms** are not BEES's (ruled); the payload is the typed subset. `float16`, tagged tuples, non-ASCII text, maps and sets as message types: not covered (M1b).
- **`make measure` is not part of `make integrate`**: its numbers vary and the run takes minutes.
- **The root supervisor:** the programs spawn plainly, as in M3 (a compiler lowering must add `conn`, `tx`, the proxies, the deliverers and now the assemblers to its root supervisor and give them ids from its pool).
