# BEES minimum viable product: messages across nodes

**Status: proposed 2026-11-04; revised the same day to work with standard Silica and to use the Erlang distribution protocol (D34). Milestones M0 to M5 are done (2026-11-06); the wire is written down in [contract/wire-v1.md](../contract/wire-v1.md). Revised 2026-11-06 (D36 to D38): BEAM mode and TRUST mode are two separate implementations, the next stage is the milestone list N0 to N5 in section 5, and the configuration file is designed in [bees-config-file.md](bees-config-file.md). Nothing of N0 to N5 exists yet. Update 2026-11-06 (verified by the user and the parent, read-only checks of the Silica tree): the newest compiler binary, `silica-999935-macos-applesilicon` (now pinned in `tools/silica.generation`), HAS the language's derived `encode((:etf), value)` and `decode((:etf), frame)`, which replace `recreate`, and ships the hosted `(:tcp)` carrier and `wireframe`; BEES's own M2 carrier, typed codec and receive stub are therefore **replaceable by the language's**, and the plan below adopts them. BEES's code as built in M0 to M5 still uses its own, until it is ported (N0.0).** The first thing BEES ships that two
separate programs can use together. It is small on purpose and is meant to be built on. Companion documents:
[roadmap.md](roadmap.md) (decisions D1-D38 and milestones), [gap-ledger.md](gap-ledger.md),
[inter-nodal-modes.md](inter-nodal-modes.md) (the full design this grows into), [bees-config-file.md](bees-config-file.md) (`bees.config`, a design).

## 1. Definition

Two programs, each a **node** in its own operating-system process, exchange messages over a local network connection.
The programs are **ordinary Silica programs**: they use Silica's own actors, supervisors, spawn, `cast_registered`,
operators and types exactly as the Silica specification describes, and nothing in their source mentions the network.
A message cast to a name that lives on the other node is delivered there.

**Done when** a demo of two plain Silica programs passes its trials: a client on node b casts typed messages
(integers, floats, booleans, strings, atoms, tuples, records and lists) to a service on node a with ordinary Silica code;
the service answers by casting back; malformed and hostile frames are refused without harming the receiver; losing the
peer does not crash the sender; and message rate and memory are measured.

## 3. What the MVP contains

### 3.1 The schema: telling BEES which messages cross

Silica types are structural and Silica has no reflection, so a program states, in a small manifest file read by
`bees_config`, which remote actors it talks to and what message each accepts. The message type is written as Silica's
own type syntax, so it is the same text the actor's behaviour declares. Proposed (format open, section 9):

```
node   b
peer   a   127.0.0.1  7001  dial
remote counter @ a   cast  { op: atom, n: int64, reply_to: atom }
local  inbox         cast  { total: int64 }
```

- `remote name @ node cast <type>`: a name that lives on a peer. `bees_config` generates a **proxy actor** registered under
  `name` on this node. It is an ordinary cast-only Silica actor whose message type is `<type>`.
- `local name cast <type>`: a name on this node that the peer may cast to. `bees_config` generates the decoder that
  delivers to it with `cast_registered`.
- Every message type is found by its **name** (M1b: the registered name of a REG_SEND, which is an atom the build adds to `bees_atoms`; the
  numeric kind id and the schema digest of M1 are gone).

### 3.2 Units

| Unit | Role |
| --- | --- |
| `bees_wire` (generated parts and a small hand-written core) | Generated per message type: an encoder from the typed value to bytes and a decoder back. The core holds the byte, integer, float and string primitives (lookups and same-type arithmetic, no type conversion, as proven in spike S5). |
| `bees_ingress` | The security boundary. Checks every frame before and while it is decoded: size, nesting depth, element counts, text in strings and atom spellings (ASCII only in the MVP), kind id known, and that every atom is already held by the program. **In M1 these checks live inside the decoder, in `bees_wire` (they must run before anything is allocated, so they cannot be a separate pass); the `bees_ingress` unit of M3 adds the audit entry and the delivery policy and calls them, rather than repeating them.** Any failure drops the frame silently toward the peer and writes an audit entry. |
| `bees_net` | The node: its name, the peer table, one **connection actor** per peer, the generated proxies and inbound deliverers. |
| `dangerous_bees_net` and the native edge | A small C archive and its Silica adapters: listen, accept, connect, write, read, poll with a timeout, close, on `127.0.0.1` only. Bytes cross in 8-byte words until `buf(uint8)` crosses the foreign-function boundary. |
| `bees_peers` and the proxy/deliverer units | **Generated** by `bees_config` from the manifest. |

Everything runs under the program's root supervisor, with the BEES listener and hub, as the compiler guide requires. A
proxy is a supervised child like any other actor.

### 3.3 Sending, receiving and failure

> **Design rules added 2026-11-06 (two user rulings; both are the REQUIRED design for N0 to N5; neither is built in BEES's code yet; the language's calls exist on the 999935 binary, and what is still unproven is the taint check on bytes that come from a carrier: see section 4).** (1) Every conversion between a typed value and transport bytes (ETF), in BEAM mode and in TRUST mode, happens in the `sequence` portion of a `sequence ... produces pure ... end` block: the **encode** (value to bytes, the language's `encode((:etf), value)`) and the **decode** (bytes to value, the language's `decode((:etf), frame)`) are each inside such a body, whose result is `produces pure`, so that no tainted value is ever sent or received across an actor boundary or by a cast, in either direction. This is exactly how the language's own `transport_beam_demo` uses them in the owner's handler. (2) A transport connection has **exactly one actor wrapping the send buffer and one separate actor wrapping the receive buffer**, described below.

**The two actors of a connection.**

| Actor | Owns | Does | Boundary |
| --- | --- | --- | --- |
| **send actor** | the outgoing buffer | receives a typed value (or a built control message), **encodes it inside its sequence / `produces pure` block**, and hands the bytes to the carrier in the carrier contract's `:tx` messages, honouring `:tx_credit`; sends the net tick when idle; reports `:tx_failed`/`:link_down` onward | nothing tainted enters it (its input is typed values from proxies or the TRUST server and client code); it receives no carrier read events |
| **receive actor** | the incoming buffer | takes the bytes the carrier delivers (`:rx`), assembles a frame, **decodes inside its sequence / `produces pure` block**, and delivers typed values onward (to the deliverer for a registered name in BEAM mode; to the TRUST connection logic in TRUST mode) | the carrier's receive events are the only tainted thing it sees, and they are consumed inside that block; only the `produces pure` result leaves it |

Both modes use the same two actors per connection. In **BEAM mode** a link has one pair for its life (ticks, `REG_SEND` and, from N2, the cookie steps and control messages). In **TRUST mode** a connection carries one request (the B1 behaviour, N3, N4) or a bounded session of several (B2, N5), and each connection, short-lived or not, has its own pair; the multiplexing design's worker-per-request and per-connection supervisor sit **behind** the receive actor and **in front of** the send actor, so a worker neither reads nor writes the carrier.

**What M3 and M4 built, and what would change.** M3 built the writer `tx` (the one writer: it also owns the idle timer and the net tick) and the connection actor `conn` (the carrier's owner and the receive state machine: the handshake and framing steps); M4 added a per-frame assembler `asm` that `conn` spawns for each frame and forwards each received part to, because `conn`'s state may hold no heap value (SD-35: an actor state with a heap value takes the whole-state copy at every dispatch and grows by about 1 MiB of committed memory per dispatch, never returned). Mapping: `tx` is already the send actor in role, with two differences to remove (it carries the idle timer and the reaper call, and it receives already-encoded frames built by the proxy, not typed values: the encode moves into it). The receive side is where `bees_net` changes: `conn` plus `asm` become **one receive actor that is the carrier's owner and owns the incoming buffer**, and the per-frame `asm` hop disappears if the buffer can be held without a heap value in state. **That is the open constraint: SD-35 forbids keeping a heap-valued buffer in an actor's state, and a buffer cannot be in an actor's initial state (E4038).** Options, to be settled in N0 once the checker trial (section 4) has run: (a) the receive actor keeps the buffer in a region it is handed by the carrier per frame (a message carries a buffer only with its region), builds nothing in state, and decodes in the same dispatch that receives the last part, so the assembler is absorbed; (b) if that does not pass, `asm` stays as a short-lived helper owned by the receive actor and the decode happens in `asm`'s block. Either way the carrier's event type and the writer's role do not change. **With the language's `wireframe@frame` and `wireframe@unframe` (4-byte length framing, with the maximum frame size an argument) the receive actor no longer assembles parts by hand in BEES code**: the carrier delivers segments, `unframe` reassembles them (its state is a small record: mode, expected length, pending string), and the frame is decoded in the same block; that is why the assembler may disappear. `wireframe` has no 2-byte form, so the handshake's 2-byte framing stays BEES's own. Timers, the reaper and the tick move out of the writer only if the trial shows they must.

- **Send.** The user's code casts to the name. The local proxy receives the typed value, encodes it into a `send` frame
  and passes the bytes to its connection actor, which writes them through a `dangerous_` writer worker.
- **Receive.** A `dangerous_` reader worker per connection reads whole frames in word-sized calls and casts the raw words
  to the connection actor. The connection actor **re-creates** the frame (section 4), runs `bees_ingress`, decodes it to a
  typed value in a fresh region, and delivers it with `cast_registered` to the local name for that kind id. If no actor
  holds the name, the message is dropped and counted.
- **Reply.** There is no new mechanism. The request carries a `reply_to` name (an atom field in the message, as the
  Silica specification's own examples do with `reply_to`), and the service casts its answer to that name. On the service
  node that name is a proxy for an actor on the client's node.
- **Failure maps onto Silica's own rules, with no new failure kind.** When a connection is closed or fails, its proxies
  end themselves with `fail_self` and a reason. A cast to an ended actor fails the sender in Silica, so a sender
  learns of a lost peer the way it learns of any dead actor, and the supervisor restarts the proxy. There is no
  reconnect in the MVP, so a restarted proxy drops its messages until the program restarts the connection.

### 3.4 The wire: the Erlang distribution protocol (D34)

> **D35 (2026-11-05).** Silica's branch `binary-transport-support` designs ETF encoding, framing and carriers as language features (not yet built). What this section describes for typed messages is BEES's interim of that design; the distribution protocol layered above it is BEES's lasting part. See [silica-transport-alignment.md](silica-transport-alignment.md). **Update 2026-11-06: `encode`/`decode((:etf), ...)`, `wireframe` and the hosted `(:tcp)` carrier are in the newest binary (999935), so this interim is now replaceable; section 5, N0.0 and N1.**

BEES uses **only the latest version of the protocol**. That is handshake **version 6**, the only version in the range of the
installed OTP 28 (`ERL_DIST_VER_LOW` and `ERL_DIST_VER_HIGH` are both 6). Nothing older is spoken: no `n` send-name message
of OTP 22 and earlier, no flag sets for older peers, no atom-cache negotiation. **The layouts below were read from the installed
OTP 28 source** (`kernel-10.0`, `dist_util.erl` and `dist.hrl`) **and the pid encoding was checked with `term_to_binary`.** The
ETF layouts for the other types were checked against vectors from `erl` in milestone M1b.

**Distribution flags.** A node sends 8 bytes of flags. The flags OTP 28 makes mandatory, which BEES must set, are the OTP 25 set
(extended references `0x4`, fun tags `0x10`, new fun tags `0x80`, extended pids and ports `0x100`, export pointer tag `0x200`, bit
binaries `0x400`, new floats `0x800`, UTF-8 atoms `0x10000`, map tag `0x20000`, big creation `0x40000`, handshake 23 `0x1000000`)
and the OTP 26 pair (`V4_NC` `0x4_0000_0000`, unlink id `0x200_0000`). Their union is `0x4_0307_0F94`. Whether to add the
OTP 25 digest shorthand flag (`0x400_0000`) is open (section 9). BEES does not offer the atom-cache flags, the distribution header,
fragments or the other optional flags in the MVP.

**Handshake messages (version 6), with 2-byte length framing until the handshake ends:**

| step | tag | contents |
| --- | --- | --- |
| initiator sends | `N` | flags (8 bytes), creation (4), name length (2), node name (latin-1; ASCII here) |
| acceptor replies | `s` | status text, `ok` to continue |
| acceptor sends | `N` | flags (8), challenge (4), creation (4), name length (2), node name |

The acceptor's `N` has a challenge field. **As built in M3 there is no challenge reply, no acknowledgement and no digest**: OTP's cookie scheme
(`r`, `a`, and an MD5 over the cookie and the challenge) is not spoken, and the challenge
field is sent as zero and ignored. **Amended 2026-11-06 (D36): BEAM mode will use Erlang's cookie authentication** (the challenge in the acceptor's `N`, the dialer's `r` carrying its digest and its own challenge, the acceptor's `a`), because stock nodes require it; that is milestone N2, built from the installed OTP 28's `dist_util.erl`. The MD5 digest and the random challenge come through the native edge, system libraries only. A node name the program does not hold is
refused (D16).

**Security.** *Amended 2026-11-06 (D36): the earlier text here said the whole distribution stream would run inside TRUST's mutual TLS 1.3. That is withdrawn.* TRUST is a **separate implementation** with its own wire (SEMP's: a 4-byte length and an ETF map per frame, mutual TLS 1.3, ALPN `trust/1`, peers identified by the SHA-512 fingerprint of their certificate); it is not layered around the distribution protocol and cannot talk to a regular BEAM node. **BEAM mode authenticates with Erlang's cookie** (N2) and, later, may use the `inet_tls_dist`-compatible TLS profile (D25). **Until N2 the MVP has no authentication and no encryption**: it
binds to `127.0.0.1` and is test-only.

**After the handshake**, frames carry a 4-byte big-endian length. A zero length is a net tick: **each side sends one when it has been idle for the tick interval, and a received tick is counted, not answered** (corrected in M5; an echo of every tick would ping-pong for ever, and it is what OTP does; see [contract/wire-v1.md](../contract/wire-v1.md) section 4.2). A message
is the byte `p` (pass-through), then the control message as ETF, then the payload as ETF. The MVP sends and receives one
control message, `REG_SEND` (`{6, FromPid, '', ToName}`), which is exactly "send to a registered name on that node". Any
other control message is dropped and counted. `FromPid` is a pid of the sending node built from the sending proxy's 64-bit
identity: a `NEW_PID_EXT` (tag 88: the node as an atom, a 4-byte id, a 4-byte serial, a 4-byte creation), checked against
`term_to_binary(self())` on OTP 28, which maps onto the 32-bit spawner position and 32-bit child number.

**ETF, from the declared Silica type** (the target name fixes the type; there is no message-kind id on the wire):

| Silica type | ETF |
| --- | --- |
| `int8` to `int64`, `uint8` to `uint64`, `char` | the smallest of small integer, integer, small big; the decoder accepts any valid encoding that fits the type, and refuses anything outside its range |
| `float32`, `float64` | new float (8 bytes, IEEE 754 big-endian); a `float32` is refused if the value does not fit exactly; infinity and NaN are refused |
| `boolean` | the atoms `true` and `false` |
| `atom` | small atom UTF-8 or atom UTF-8, by spelling; refused if the program does not hold it (D16) |
| `string` | binary |
| tuple | small tuple (large tuple above 255), components in order |
| record | map with atom keys, written in name order and read in any order (M1b; the language's rule, silica-transport-alignment.md section 3) |
| `List[T]` | list with a nil tail; the empty list is nil; a list of integers or chars that are all 0 to 255 is a string ext, as erl writes it |

The decoder checks the whole term against the declared type and refuses a mismatch, an unknown tag, a bad length, a non-proper
list, or a term outside the limits. **The M1 rules carry over (the text rule widened to all of ASCII, 0 to 127, in M1b):** text is ASCII only, the limits (frame 4 KiB, depth 16, 256
list elements, atom 255 bytes, string 1 KiB), bounds-checked reads that reject instead of faulting, and nothing allocated
before the checks. **Not in the MVP:** pids, references, ports and funs as typed values (a pid is a term), maps as terms, big integers beyond 64 bits, atom
caches and the distribution header, compressed terms, atoms outside ASCII, tagged tuples.

**The manifest** keeps `message <name> <silica type>` and adds (built in M3, format in `tools/bees_dist_gen.py`): this node's name, `peer` lines (name, host,
port, `listen` or `dial`), and `remote` / `local` lines that tie a registered **name** to its message type. Kind ids and the
schema digest from the first codec are no longer on the wire; a schema mismatch shows up as a refused frame.

### 3.5 The connection

1. The dialing node connects and runs the handshake above; the listening node checks the peer's name against its peer table.
   On any failure it closes the connection.
2. After the handshake, either side sends `REG_SEND` messages and net ticks. A frame before the handshake completes is dropped.
3. A tick is sent when the connection has written nothing for the tick interval (`tick_ms`, default 15 s); a peer that sends nothing for `io_ms` (default 60 s)
   is treated as lost, its connection closes and its proxies end (section 3.3). Built and tested in M3 (`ticks_alive`, `ticks_absent`).

There is **no authentication and no encryption** in the MVP, so every build prints a banner that the transport is for testing
only. The cookie digest (BEAM mode, N2) and TRUST's own transport (N3 to N5) are separate later pieces; neither wraps the other.

## 4. The gate: receiving bytes from the network

Bytes returned by a foreign call are **tainted**, and Silica's rules stop a tainted value leaving the handler that
receives it. **Update 2026-11-05:** Silica dropped both marker traits (`Transportable`, `Recreatable`; `impl Transportable` is now E2411) and
replaced them with derived calls that take their limits as arguments. **Update 2026-11-06 (checked read-only against `silica-999935`):
the language now HAS `encode((:etf), value) -> string` and `decode((:etf), frame) -> (:ok, T) | (:rejected, atom)`
(T from the declared pattern), and they replace `recreate`** (`decode` and `recreate` are one mechanism). The earlier finding of
M3, that the linked binary `silica-999936` had none of them (`trials/m3_decode_probe`: E2007; SD-32), is **resolved on 999935**
([silica-defects.md](silica-defects.md)). The parent's probe `trials/m3_decode_probe` (rewritten) confirms on the 999935 binary that encode
then decode of a tagged tuple holding a record round-trips inside a `sequence ... produces pure` block and that the first byte is 131; it
uses no foreign-function bytes, so it does not test taint. The language's `transport_beam_demo` (in the Silica tree, not BEES's) uses both
calls in the sequence of such a block in an owner's handler, over the hosted `(:tcp)` carrier and `wireframe`.

**Milestone M0 was run on 2026-11-04** ([spikes/S8-hand-recreation.md](spikes/S8-hand-recreation.md)) to see whether BEES
could re-create received bytes by hand, rebuilding each value from literals by branching on the tainted bytes. **It
cannot.** Silica's checker treats every value derived from a tainted one as tainted, a `case` over literals included, and
rejects it in the worker's `produces pure` (E2100).

**What BEES's code does today (M3 to M5, built on 999936; decision to review):** the receive step is one function, `bees_ingress@recreate`, a **stub**. It copies the
parts the transport delivered into a frame buffer; it does not clear taint, and it works only because the handler that receives
an FFI result is not checked (SD-25). Everything after it is BEES's own validation: bounded frame length before any byte is
stored, bounds-checked reads that reject instead of faulting, the sender's pid checked against the connected peer, a target name
that the program lists, the payload validated against that name's declared type before anything is decoded. That is
**safe against malformed and hostile bytes in the sense of "cannot fault or exhaust the receiver"**, and it is **not** the
language's taint guarantee: the compiler cannot vouch for it, and a compiler that starts checking handlers will reject it.
**It is to be replaced by the language's `decode` inside the receive actor's sequence (N0.0); until that port the code, and every statement about it in M3 to M5, still describes the stub.** Its limits then become the call's and `wireframe@unframe`'s arguments; nothing else changes. **M4 note:** the parts of a frame are now collected by a per-frame assembler actor (the connection actor's state may hold no heap value, SD-35), which calls `bees_ingress@recreate`; the stub is still the one function.

**The required design from 2026-11-06 (user ruling): conversion happens inside `sequence ... produces pure`.** For every conversion step in both BEAM mode and TRUST mode, the encode (value to ETF bytes) and the decode (ETF bytes to value) are each performed in the `sequence` portion of a `sequence ... produces pure ... end` block (the form the foreign-function specification uses for the worker of a dangerous call), and the block's result is `produces pure`. Then no tainted value is sent or received across an actor boundary or by a cast, in either direction: the carrier's received bytes are consumed inside the receive actor's block and only a pure, typed value leaves it; what the send actor hands to the carrier is built from pure values. This replaces the stub of this section as the target; the stub stays until the form is shown to work.

**What is known and what is not (2026-11-06).** Known: the derived `encode` and `decode((:etf), ...)` exist on 999935, and encode-then-decode round-trips inside a `sequence ... produces pure` block (the parent's probe); the language's own demo does the same with bytes that arrive from its carrier, and suggests that this passes the taint checker end to end. M0 ([spikes/S8-hand-recreation.md](spikes/S8-hand-recreation.md)) found that a **hand-written** rebuild inside a worker's `produces pure` is rejected with E2100, and SD-25 says the handler of an FFI-result cast is unchecked; both are about BEES doing the rebuild itself, which the rule avoids. **Unproven, because BEES has not tested it with its own carrier:** whether `decode` applied to bytes that came from a carrier or foreign-call result passes the taint checker end to end, in the receive-actor shape with a bounded buffer in state (SD-35). This document does **not** claim that it works for BEES's use. Milestone N0 has two first tasks: **N0.0 ports the M3 receive path to the language's `decode` and `wireframe` on the 999935 binary and re-runs the M3 and M4 trials**, and **N0.1 is the narrowed taint trial** (conversion in the sequence of `produces pure`, **with bytes that came from a carrier**, in both directions), recorded in [silica-defects.md](silica-defects.md) with what must change if it fails (a Silica change, a different boundary, or staying on the stub with its caveat). Nothing in N1 to N5 may be called secure in the language's sense before that result is in.

## 5. Milestones

> **Reading M3 to M5 after 2026-11-06.** Their rows say the receive step is a stub because `decode`/`recreate` were not callable in the linked compiler (SD-32). That was true of `silica-999936`, on which they were built; **it is resolved on 999935**, where the language has `encode` and `decode((:etf), ...)`, `wireframe` and the `(:tcp)` carrier. The rows are kept as the record of what was built and measured; the code they describe is the stub until N0.0.

Each milestone ends with trials in `trials/`, run by `make -C trials integrate`; the paired-process ones also run through
a small driver script that starts two executables and compares their outputs.

| Sum types, optional references, maps and sets, `buf` | Added to the codec one at a time. |
| Sends to a pid, links, remote spawn, node-down notification | After the MVP, once an identity-to-actor table or Silica's registry exists. |
| EPMD discovery, and interoperating with stock Erlang nodes | **Planned: N2** (roadmap D36, D38): BEAM mode with Erlang's cookie digest, EPMD registration and lookup, and a live test against `erl -sname`. Not in the MVP. |
| TRUST | **Planned: N3** (logic over plaintext loopback), **N4** (mutual TLS 1.3 after the TLS engine decision) and **N5** (multiplexing). TRUST is its own implementation, not a wrapper around the distribution stream (D36). |
| Pids, references, ports and funs as values; links; remote spawn; the distribution header and atom cache | Later control messages and terms on the same protocol (roadmap B3, B4). |
| Reconnect, backoff, flow control, more than one frame in flight | A later step on the same connection actor. |
| More than two nodes | The peer table already supports it; the demo uses two. |
| Frames larger than 4 KiB | The limit becomes a `bees.config` option in **N1**, with BEAM's own limit (4294967295 bytes) as default and ceiling (R1, ruled 2026-11-06), passed to the language's `wireframe` and `decode`; how fast a large frame crosses is measured on the language's carrier in N1. |
| Windowed multiplexing and cancel-by-close | **N5** (roadmap B2). |

## 8. Risks

- **The receive step is still the stub in BEES's code** until N0.0 ports it to the language's `decode` (available on 999935); whether that passes the taint checker with carrier bytes is untested (N0.1). Mitigation: it is one function, `bees_ingress@recreate`; everything after it validates.
- **A generator must understand Silica type syntax.** It reads a restricted subset of the type grammar. Mitigation: start
  with records, tuples, `List[T]` and the primitives; reject the rest at build time.
- **Word-sized foreign calls are slow.** 4 KiB is 512 calls per frame. Measured in M4: a 600-byte frame (75 parts) each way, about 50 ms per request/answer round trip, 19 round trips per second in one run; acceptable for the MVP, not for more.
- **The proxy is a second name registered under the same atom as the remote actor.** The name must not also exist locally;
  `bees_config` rejects a manifest that declares a name both ways.
- **One listener for exits.** The failure listener handles about 20,000 reports per second and sees every actor end; not
  an MVP concern unless the demo spawns heavily.
- **Silica's failure-report text is the listener's interface.** A change to it breaks exit tracking, not message passing.

## 9. Open points for a human

   the tick time. These are read from the installed OTP 28 and still to be checked by running two BEES nodes.
2. ~~Whether the Erlang name-and-flags exchange stays at all once TRUST's TLS authenticates the peer.~~ **Moot (D36):** TRUST does not use the distribution handshake at all, and BEAM mode keeps it whole, with the cookie steps added in N2.
3. The manifest lines for the node name, peers and remote and local names (M3).
4. The proposed limits (frame 4 KiB, depth 16, 256 list elements, atom 255 bytes, string 1 KiB), now measured against ETF.
5. Whether a cast to a name nobody holds should leave an audit entry (proposed: yes, counted, not per message).
6. Whether a lost connection should end its proxies (proposed) or leave them running and drop silently.
7. How a `float32` that does not fit exactly, and a `uint64` above the `int64` range, should be handled when ETF can carry them
   (proposed: refuse the first, accept the second as a small big).
8. ~~Whether a compatibility mode for stock Erlang nodes (cookie authentication) is wanted.~~ **Decided 2026-11-06 (D36): yes, as BEAM mode proper (N2), not a downgrade of TRUST.**
